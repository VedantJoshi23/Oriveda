    Plate 01IntroductionSource · ORIGIN.md

    Oriveda is an engineering knowledge framework for building software with AI agents.

    Its name joins guided vision with foundational knowledge.

    Its rule: specs before code, evidence before specs.

    Oriveda

    Engineering the Future, Deliberately.

    Ori·ve·da n.
    1Ori-, from Orion, humanity's oldest navigation aid: guided vision.
    2-veda, from the Vedas: foundational knowledge.
    3An engineering knowledge framework for building software with AI agents.

    Specs before code. Evidence before specs.

    Plate 02The problemSpecimens are illustrative · claim from README § Vision

    Software loses knowledge faster than it gains code.

    Architecture decisions vanish into chat threads. Business rules hide inside code.

    Documentation drifts out of date, and every new AI session starts from zero.

    Oriveda treats that knowledge as the durable asset, and the code as one consumer of it.

    Oriveda writes knowledge down before it is built, instead of reconstructing it afterwards from commit history and chat logs.

    Plate 03Why layersSource · ORIGIN.md § The crack in the plan

    One giant prompt can't work.

    Oriveda began as a request for one complete prompt to hand to any coding agent.

    But its parts change at different rates. Change one feature and you'd regenerate everything.

    So the prompt split into layers, and became documentation the code must answer to.

    ONE MASSIVE PROMPT engineering philosophy · modular monolith · domain boundaries · coding standards · API conventions · auth · sessions · caching · load balancing · error tracking · disaster recovery · checkout flow · wishlist · coupons · order status · inventory · payments · email templates · admin roles · deployment · logging · rate limits · feature flags · and every feature still to come …

    Architecturerarely

    Featuresconstantly

    each tick is a changetime →

    Layered, versioned and stable enough to build on, a prompt isn't a prompt anymore. It's documentation.

    Plate 04Evidence firstClaims are illustrative · method from OV-000

    Every claim carries its evidence.

    Start from whatever you actually have: code, a PRD, Figma, screenshots, or just an idea.

    Each extracted fact becomes a claim with a confidence score and a citation to its source.

    Facts, inferences and assumptions are labelled. An assumption is never treated as settled.

    Instead of generic questions, the agent asks only for the evidence that would raise confidence most.

    Most AI tools start with code. Most docs start with requirements. Oriveda starts with evidence.

    Plate 05MilestonesSource · README § Knowledge Hierarchy, ADR-0005

    Implementation is the last milestone, not the first.

    Knowledge is built in a deliberate order, with one protocol per milestone.

    Significant decisions are recorded as ADRs wherever they happen. They cut across every layer.

    You don't finish every milestone first. Go just deep enough for one feature, build it, then deepen the specs with what the build taught you.

    Plate 06Progressive rigorSource · ADR-0005

    Freeze on proof, not on paper.

    A spec's status decides its authority over the code.

    Its risk decides when it must be Frozen. Work may start on a Draft whose claims are at least 60% confident and owner-acknowledged.

    Disagreements with a Draft aren't failures. They're logged, reconciled, and resolved before it freezes.

    Frozen
    Binds the code. When code disagrees with it, the code is wrong.
    Draft
    Informs the code. A disagreement is a divergence: logged, and either side may change.
    RiskCoversFrozen before
    HighConstitution, domain boundaries, data ownership, auth, paymentsany code that touches it
    MediumMost domain and feature specs, Standardsthe first release that ships it
    LowRoutine features, written as a short spec cardthe first release that ships it

    Plate 07The engineReal run · engine walkthrough, output abridged

    Check the code against what you decided.

    Code graphs tell you what the code is. The oriveda engine tells you whether it matches what you decided.

    It compares every cross-domain dependency in the code with each domain's declared boundaries.

    Against a Frozen spec, a forbidden dependency is a violation.

    Against a Draft spec, it's a divergence, reported with a ready-to-paste divergence-log row.

    This is a real run, against the open-source RealWorld NestJS app.

    Plate 08PrinciplesSource · README § The Oriveda Principles

    Eight principles hold it together.

    Code changes. Frameworks change. Languages change. Engineering principles should not.

    The lens for every decision: if this grew to 100 engineers and 10 million users, would it still make sense? If not, why is it acceptable today?

    Not every shortcut must scale. Every shortcut must be intentional, and written down.

    1. 01Knowledge outlives implementation.It survives framework migrations, language changes and rewrites.
    2. 02Every decision is discoverable.Never only in a conversation.
    3. 03Every spec has one purpose.A single responsibility and a clear owner.
    4. 04Documentation is executable knowledge.A Frozen spec is the authority on behaviour.
    5. 05Humans and AI read the same knowledge.No tribal knowledge in chat transcripts.
    6. 06The framework evolves independently.Reusable across products and domains.
    7. 07Every shortcut is intentional.Written down with its rationale and migration plan.
    8. 08Consistency beats cleverness.Predictability creates maintainability.
    Plate 09Get startedSource · README § Quickstart

    Start with one prompt.

    Bring whatever evidence you have: a repo, a PRD, screenshots, or nothing but an idea.

    From inside your own project, give your coding agent this 

    You are setting up this project to be governed by the Oriveda engineering
framework (https://github.com/VedantJoshi23/Oriveda). Add it as a git
submodule at .oriveda-framework/, then start with PRM-DISCOVERY: ask me
what evidence I have about this project (existing code, a PRD, Figma,
screenshots, a video — anything) and begin Knowledge Acquisition from
whatever I actually have.
